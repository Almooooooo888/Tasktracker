# Taskboard для Jira

Локальный Taskboard показывает задачи выбранного пользователя, помогает вести регресс и собирать релиз по Fix Version. Вкладка **«Созданные баги»** показывает баги автора из Jira-токена по дням создания, включая закрытые. Раздел **«Разбор обращений»** ищет запросы и уведомления по регистрационному номеру или UUID, сопоставляет закрытый и открытый контуры и показывает адресные логи Kubernetes, если настроен доступ к кластеру. Вкладка **«Календарь»** читает события Exchange после отдельного входа. Вкладка **«Стенды»** показывает развернутые версии сервисов DEV и QA.

## Запуск

В Windows запусти `Start.cmd` из этой папки. Для Docker собери локальный образ командой `docker compose up -d --build` и открой `http://127.0.0.1:18764/`. Каждый пользователь вводит свой Jira PAT в настройках приложения. GitLab для поиска MR и веток настраивается там же отдельным токеном с правом `read_api`.

Docker Hub-файл `compose.hub.yaml` пока указывает на прежний тег 1.18.0; публикация этого тега здесь не подтверждена. Разбора обращений, списка созданных багов и стендов в прежней версии нет. Локальный код и собираемый из него образ имеют версию 1.23.0.

## Стенды

Вкладка читает только Deployment и pod в namespace `development` (DEV), `development-dev-3` (DEV-3), `development-qa-2` (QA-2) и `development-qa-3` (QA-3). Для каждого контейнера показаны образ из Deployment, теги работающих pod и готовые/желаемые реплики. Во время выкладки разные версии pod видны одновременно. Снимок обновляется каждые 15 секунд, пока вкладка открыта; изменение версии выделяется на пять минут. Нужны `kubectl`, рабочий kubeconfig и право чтения этих namespace. В Docker этих зависимостей по умолчанию нет.

Если GitLab настроен в профиле, Taskboard ищет проект в группе `digital` и её подгруппах и добавляет ссылку только при однозначном совпадении имени проекта с именем образа. Отсутствие ссылки не означает отсутствие репозитория. Тег образа не считается доказанным коммитом Git: SHA показывается только при наличии явной аннотации Deployment. Текущую версию определяет Kubernetes, а не последний коммит или тег GitLab.

## Календарь Exchange

Для локального запуска Windows укажи в игнорируемом Git файле `diagnostics.local.json` значения `exchangeDomain` и `exchangeAutodiscoverUrl` по образцу `diagnostics.local.example.json`. Также можно передать `LK_EXCHANGE_DOMAIN` и `LK_EXCHANGE_AUTODISCOVER_URL` через окружение. Адрес Autodiscover и обнаруженный адрес EWS должны использовать HTTPS и находиться в разрешённом домене. Docker-образ не содержит Windows PowerShell, поэтому календарь в Docker пока недоступен.

Открой **«Календарь»**, введи адрес ящика, корпоративный логин и пароль. Taskboard получает адрес EWS через Autodiscover и читает календарь через `FindItem`/`CalendarView`; письма и вложения не запрашиваются. Пароль передаётся локальному серверу через loopback и хранится только в памяти процесса до выхода или перезапуска. События выводятся по месяцам; Exchange ограничен первыми 500 событиями за месяц, и приложение явно помечает такой результат как неполный. Кнопка «Участники» у встречи читает её организатора и приглашённых через `GetItem`; выбор человека запрашивает его календарь на тот же месяц. Чужой календарь откроется только при наличии прав просмотра в Exchange, иначе приложение покажет отказ. Реальный вход и чтение событий зависят от прав Exchange и проверяются после ввода своей учётной записи в приложении.

## Созданные баги

Вкладка читает Jira от имени владельца сохранённого токена. Показываются все созданные им задачи типов «Баг», «Дефект» и «Ошибка» независимо от статуса и от пользователя, выбранного для вкладок задач. Список отсортирован от новых к старым, сгруппирован по дате создания в московском времени. Первые 100 загружаются сразу, остальные — кнопкой «Показать ещё». «Обновить» повторно читает Jira; ничего в задачах не изменяет.

## Разбор обращений

Слева открой **«Разбор обращений»**, выбери **«Запрос»** или **«Уведомление»**, введи текущий номер карточки либо полный UUID и нажми **«Разобрать»**. Оба вида хранятся как `audit_interaction`, но тип сверяется с карточкой. Номер с ведущими нулями можно вводить без них; номера регистрации и проекта САДЭД тоже поддержаны. Если после регистрации старый числовой номер был заменён и больше не хранится в этих полях, ищи по UUID. Результат содержит текущий статус, историю переходов, счётчики файлов и ответов, данные регистрации САДЭД, сопоставление контуров и адресные строки логов.

Для БД используются только параметризованные `SELECT` внутри транзакций `READ ONLY`; учётная запись БД тоже должна иметь только чтение. Адрес, логин и пароль можно ввести в разделе «Доступ к диагностике» настроек профиля. В Windows профиль зашифрован средствами DPAPI. Имена БД и схем обоих контуров задаются через игнорируемый Git файл `diagnostics.local.json` по образцу `diagnostics.local.example.json` либо переменные `LK_DB_INTERNAL`, `LK_SCHEMA_INTERNAL`, `LK_DB_EXTERNAL`, `LK_SCHEMA_EXTERNAL`. Адрес, логин и пароль также можно передать через `LK_PG_HOST`, `LK_PG_USER`, `LK_PG_PASSWORD`. **Пароль БД не хранить в файле проекта.** Docker Compose передаёт переменные из окружения хоста, если они заданы.

Для поиска логов нужен `kubectl`, путь к рабочему kubeconfig в настройках профиля или переменной `LK_KUBECONFIG`, а также список namespace и префиксов pod в локальном файле конфигурации. При необходимости укажи `LK_KUBE_CONTEXT` и `LK_KUBECTL`. Настройки одного стенда нельзя автоматически применять к другому. Без kubeconfig разбор БД работает, а логи явно помечаются как недоступные. В Docker для логов дополнительно нужны установленный `kubectl` и смонтированный kubeconfig; образ по умолчанию их не содержит.

Логи читаются только за выбранное окно и из последних 2000 строк не более восьми подходящих работающих pod в каждом namespace. Непроверенные pod и ошибки доступа показываются отдельно. Отсутствие совпадения в таком окне не доказывает отсутствия события. Диагностические правила отделяют подтверждённый окончательный сбой от ожидания с повторами; общий `REGISTERED_FILES_DOWNLOAD_TIMEOUT` без исходной причины не называется ошибкой PDF или DELOM. Наличие карточки в обеих БД не подтверждает работу UI или полный маршрут Kafka.

## Безопасность и конфигурация

Профиль с токенами остаётся локальным. Windows хранит его через DPAPI, Docker — в отдельном томе, доступном администраторам Docker. Не коммить `.env`, `diagnostics.local.json` с внутренними адресами, сертификаты, профили и токены. Порт опубликован только на loopback-интерфейсе.

Docker проверяет TLS-сертификат Jira по умолчанию. Для внутреннего CA положи публичный PEM в `certs/jira-ca.pem` и настрой `NODE_EXTRA_CA_CERTS=/run/certs/jira-ca.pem`; закрытый ключ и личный PFX не копируй. Windows-запуск сейчас воспроизводит поведение версии 1.17.0 для внутреннего dev-сертификата Jira и отключает его проверку.
